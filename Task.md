# Mini API — SQL Server

## 1. Assignment Overview

Build a small versioned HTTP API for managing training courses. Store all course data in SQL Server through plain JDBC, and load database connection details from a configuration file.

### Learning outcomes

- Implement five versioned CRUD endpoints using JSON and appropriate HTTP statuses.
- Paginate collection results with stable ordering and pagination metadata.
- Load database connection settings from a configuration file.
- Separate HTTP handling, business logic, and JDBC data access.
- Validate input and return consistent error responses.
- Use PreparedStatement, generated keys, and try-with-resources correctly.
- Verify API behavior with Postman, including persistence after an application restart.

## 2. Tools, Prerequisites, and Scope

- **Core:** Java, `com.sun.net.httpserver.HttpServer`, and Maven.
- **Libraries:** Jackson or Gson, plus the Microsoft JDBC Driver for SQL Server.
- **Database:** SQL Server.
- **Configuration:** Load database settings from `config/db.properties`.
- **Manual testing:** Postman.

## 3. Course Model and SQL Design

### Course fields

| Field | Type | Requirement |
|-------|------|-------------|
| id | Long | Generated by SQL Server IDENTITY |
| title | String | Required; not blank; maximum 15 characters |
| description | String | Optional; maximum 50 characters |
| capacity | Integer | Required; must be greater than zero |

### Core rules

- Generate a unique ID when a course is created.
- Reject a blank title.
- Reject a capacity that is zero or negative.
- Return a not-found result when the requested ID does not exist.

## 4. Required Endpoints

All endpoints must use the `/api/v1` base path.

| Method | Endpoint | Purpose | ROLE header | Success |
|--------|----------|---------|-------------|---------|
| GET | `/api/v1/courses?page={page}&size={size}` | List courses (paginated) | Not required (public) | 200 OK |
| GET | `/api/v1/courses/{id}` | Retrieve one course | USER | 200 OK |
| POST | `/api/v1/courses` | Create a course | ADMIN | 201 Created |
| PUT | `/api/v1/courses/{id}` | Update a course | TEACHER and ADMIN | 200 OK |
| DELETE | `/api/v1/courses/{id}` | Delete a course | ADMIN | 204 No Content |

### Authentication and authorization

Use the HTTP request header named `ROLE` as a simplified access mechanism. Protected endpoints authorize only the uppercase role shown in the table above; roles do not inherit permissions.

- `GET /api/v1/courses` is public and must work without a ROLE header.
- Accepted protected-endpoint values are `USER`, `ADMIN`, and `TEACHER`.
- Return **401 Unauthorized** when ROLE is missing; return **403 Forbidden** when it is unrecognized or not authorized for the endpoint.

Use the consistent JSON error shape shown below for these responses. In production, derive roles from authenticated credentials instead of trusting a client-supplied header.

### Pagination

`GET /api/v1/courses` accepts optional `page` (default 1; minimum 1) and `size` (default 10; range 1–100). Invalid values return 400. Return id-ascending results with `items`, `page`, `size`, `totalItems`, and `totalPages`.

### Example create request and response

```http
POST /api/v1/courses
Content-Type: application/json
ROLE: ADMIN

{"title":"Java Basics","description":"Core Java practice","capacity":20}
```

```http
HTTP/1.1 201 Created
Location: /api/v1/courses/1

{"id":1,"title":"Java Basics","description":"Core Java practice","capacity":20}
```

### Consistent error response

```json
{
  "status": 400,
  "error": "VALIDATION_ERROR",
  "message": "title must not be blank"
}
```

## 5. Implementation Requirements

- Parse JSON request bodies and return JSON responses.
- Expose every endpoint under the `/api/v1` base path.
- Enforce ROLE at the HTTP boundary before business or repository logic; return 401 or 403 as defined in Section 4.
- Load `db.url`, `db.username`, and `db.password` from `config/db.properties`. Fail at startup if a required value is missing.
- Implement pagination in the repository with `ORDER BY id`, SQL Server `OFFSET/FETCH`, and a `COUNT(*)` query. Do not load all rows and paginate in memory.
- Validate that title is not blank and does not exceed 15 characters, description does not exceed 50 characters, and capacity is positive before calling the repository.
- Let SQL Server generate course IDs and return the created resource with a Location header.
- Keep business logic outside the HTTP handlers.
- Return consistent JSON errors; map missing courses to 404 and database failures to a safe 500 response.
- Close JDBC resources and stop the HTTP server and executor cleanly.

## 6. Manual Verification

- Use Postman to run all manual checks against the `/api/v1` endpoints.
- Verify list courses without ROLE, retrieve one with `ROLE: USER`, create and delete with `ROLE: ADMIN`, and update with `ROLE: TEACHER`; then omit ROLE for 401 and use a non-authorized role for 403.
- Create a course, retrieve it by ID, update it, and confirm the updated values are returned.
- Create or send enough courses for at least two pages. Request consecutive pages and verify stable ordering, page sizes, and pagination metadata.
- Restart the application and confirm the previously created course is still available.
- Send an invalid course request and invalid pagination values and confirm 400 responses; request a missing ID and confirm a 404 response.
- Delete a course and confirm that a later request for its ID returns 404.
